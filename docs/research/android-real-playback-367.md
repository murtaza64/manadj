# Android real-track playback — #367

Research for [native prototype #365](https://github.com/murtaza64/manadj/issues/365), distinct from the older [local-first companion map #65](https://github.com/murtaza64/manadj/issues/65) (which explicitly excluded live DJing). Earlier [runtime #151](https://github.com/murtaza64/manadj/issues/151) focused on iOS web runtimes; [sync #152](https://github.com/murtaza64/manadj/issues/152) proposes desktop-authoritative audio/analysis pull, annotation ops and append-only evidence. This note is about *native Android performance*; neither an existing mobile sync protocol nor an Android DJ engine has been implemented. [Sources: map/issue bodies; `docs/research/mobile-sync-protocol.md`](../research/mobile-sync-protocol.md).

**Near-term visual parity without PCM:** desktop [default style](../../frontend/src/waveform/styles.ts) is additive low-red/mid-green/high-blue (`[1,.1,.1]`, `[0,1,.25]`, `[.2,.45,1]`), master 0.85, group gains `[.7,1.05,1.5]`, groups 8 bands into `[0,3)`, `[3,5)`, `[5,8)`; [minimap style slot](../../frontend/src/waveform/styleSlots.ts) boosts master to 2.0. [Blob parser](../../frontend/src/waveform/blob.ts) dequantizes amplitudes as `(byte/255)^(1/gamma)` then RMS-combines bands by group; peaks and bands downsample differently (max vs mean). A synthetic *multiband* fixture can draw this appearance immediately; a single monochrome envelope cannot reveal bass/mid/high structure. [Detail renderer](../../frontend/src/components/WebGLWaveform.tsx) fixes the performance playhead at 25% across a default 20-second scrolling window ([zoom](../../frontend/src/utils/waveformZoom.ts)); [minimap](../../frontend/src/components/WaveformMinimap.tsx) maps the whole track (`x=time/duration`) with transport line moving over it. [Marker source](../../frontend/src/theme/markers.ts) specifies pink transport line 3px, orange Main cue line + bottom triangle, full 16px numbered / mini 5px unnumbered hotcue flags on 2px poles, tiered beat/phrase lines; [desktop CSS](../../frontend/src/components/Waveform.css) uses 120px detail/30px mini (phone dimensions can differ). Desktop flags currently show **slot numbers**, while backend [HotCue](../../backend/routers/hotcues.py) also carries user labels/colors; displaying readable labels on phone is an additional presentation decision. This visual pass is independent of native decoder/streaming, but the scrolling position remains illustrative until tied to the sounding clock.

## Engine options (evidence vs trial)

| Route | What sources establish | Missing proof / verdict |
|---|---|---|
| **Media3 ExoPlayer per deck**, app mixes via control volumes/individual sinks | Media3 provides media source, extraction/decoding/rendering, local/progressive media and independent speed/pitch via PCM Sonic processor. Player operations cross a message queue to playback thread; custom `AudioProcessor` chains are PCM-only; changing Sonic speed/pitch requires drain+flush. [`ExoPlayer.java`](https://github.com/androidx/media/blob/release/libraries/exoplayer/src/main/java/androidx/media3/exoplayer/ExoPlayer.java), [`DefaultAudioSink.java`](https://github.com/androidx/media/blob/release/libraries/exoplayer/src/main/java/androidx/media3/exoplayer/audio/DefaultAudioSink.java), [`SonicAudioProcessor.java`](https://github.com/androidx/media/blob/release/libraries/common/src/main/java/androidx/media3/common/audio/SonicAudioProcessor.java), [license Apache 2.0](https://github.com/androidx/media/blob/release/LICENSE). | Fast two-player *basic* playback and browse spike; **not established** sample-coherent shared mixer/clock, signed scratch, phase-aligned simultaneous launches, sample-accurate loops or central post-fader FX. Player `seekTo` is queued on playback thread; its seek response/latency on compressed local/network files needs measurement. Unmodified per-deck players are unlikely to meet desktop performance parity; useful acquisition/decoder reference. |
| **Native decoded PCM + single Oboe output callback/mixer** (recommended *parity candidate*) | Oboe wraps AAudio/OpenSL ES, can request LowLatency with high-priority output callback, and documents no blocking/alloc/file/network/lock work in callback, device-dependent stream configuration, and disconnection handling. [Oboe full guide](https://github.com/google/oboe/blob/main/docs/FullGuide.md), [Apache 2.0](https://github.com/google/oboe/blob/main/LICENSE). Android `MediaExtractor` exposes demux/sample times and seeks to sync samples, not exact decoded output position; `MediaCodec` decodes compressed frames. [AOSP extractor](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/master/media/java/android/media/MediaExtractor.java), [codec](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/master/media/java/android/media/MediaCodec.java). | Requires decode/PCM ownership, resampling, DSP, ring/chunk cache, shared mixer and frame clock; **Oboe does none of these**. Off-thread compressed seek must decode/discard to exact audible sample then prefill cache before atomic transport commit; robust behavior on MP3/AAC/VBR/stems/HTTP Range unverified. |
| **Hybrid Media3 decode + custom PCM mixer/output** | Media3's custom `Renderer`/`AudioSink` injection exists; its default sink exposes PCM processing, but also internal buffering, positioning, lifecycle and thread/message semantics. [ExoPlayer](https://github.com/androidx/media/blob/release/libraries/exoplayer/src/main/java/androidx/media3/exoplayer/ExoPlayer.java), [sink](https://github.com/androidx/media/blob/release/libraries/exoplayer/src/main/java/androidx/media3/exoplayer/audio/DefaultAudioSink.java). | Spike whether extracted decoded PCM can be fed on demand, with backseek and sample-accurate timing, without fighting player buffer/position logic. Potentially larger integration than using platform `MediaExtractor`/`MediaCodec` directly; do not promise it works from the existence of `AudioProcessor`. |

Key-lock library choices *inside* the PCM route: [Signalsmith Stretch](https://github.com/Signalsmith-Audio/signalsmith-stretch/blob/main/README.md) is MIT C++, exposes input/output latency, `.seek()` priming and split computation; read [its license](https://github.com/Signalsmith-Audio/signalsmith-stretch/blob/main/LICENSE.txt) and transitive [Signalsmith Linear MIT license](https://github.com/Signalsmith-Audio/linear/blob/main/LICENSE.txt). It claims best sound roughly 0.75–1.5× and warns debug builds are much slower; Android ABI/CPU/thermal, onset and scratch bypass remain **unmeasured**. [Rubber Band](https://github.com/breakfastquay/rubberband/blob/master/README.md) offers realtime pitch/time but is GPLv2-or-later or commercial; R3 trades more CPU for quality. Choose only after device listening, performance and intended distribution/license review. These are stretchers, not audio decoders or complete DJ engines. Existing desktop ADR leaves its stretcher choice open ([ADR 0018](../adr/0018-dual-mode-playback-worklet.md)).

## Smallest useful real-track slice → parity

1. **One legal test track, one A deck, local on-device file** (user-selected via Android document picker or a self-created synthetic WAV). Read real metadata + matching `MWF1` *if available*; otherwise show waveform pending. Decode in worker, show READY only after playable PCM primed. One master output; Play/Pause/Cue/seek audible; waveform/playhead driven from output-frame position, not Compose frame delta. Fail visibly on unsupported file/network/dropout. This proves the new command/snapshot seam without assuming LAN/server availability. [Desktop load contract](../../frontend/src/playback/DeckEngine.ts), [Oboe callback constraints](https://github.com/google/oboe/blob/main/docs/FullGuide.md).
2. **Two real decks + shared mixer**: independent deck IDs and seekable decoded source, basic crossfader/fader/trim with click-free changes, headphone PFL later. Ensure simultaneous playback plus hotcue DOWN/UP gate and load-during-play guard; label analysis origin and await real grid for auto-loop. [Desktop mixer](../../frontend/src/playback/mixer.ts), [hotcue reducer](../../frontend/src/playback/transport.ts), [grid API](../../backend/routers/beatgrids.py).
3. **Gridded transport/tempo**: beat-jump, loop/resize, quantize, pitch/bend release and BPM match/sync; verify sample-phase/loop boundaries with recorded output against grid. Then scratch signed PCM displacement, vinyl/slip/roll and key-lock stretch with bounded CPU/onset behavior. [loop](../../frontend/src/playback/loop.ts), [sync](../../frontend/src/playback/SyncGroup.ts), [ADR 0018](../adr/0018-dual-mode-playback-worklet.md).
4. **Full mixer/central FX/capture**: EQ/filter, channel/master central radio FX with tails and ceiling; meter/recording; Session events and replay on one audio epoch; Conductor takeover, then C/D CPU/memory. Stems and output/PFL routing are separately gated by device proof and product priority. [mixer](../../frontend/src/playback/mixer.ts), [FX](../../frontend/src/playback/beatFx.ts), [events](../../frontend/src/capture/events.ts), [Conductor](../../frontend/src/sets/Conductor.ts).

Seam proposal for UI3: `submit(deckId A|B|C|D, action, gestureId?, requestedAudioTime?)` for transport/continuous input; global mixer/central FX commands carry their own target; `snapshot` returns immutable deck load/track identity, audible source position, output-frame/audio epoch, cue/loop/tempo, channel levels and one FX section. UI sends capture-down/move/up/cancel and draws interpolated read-only positions from audio anchor. Command acceptance/actual application and any late async load/seek must be observable before logging as performed. Binding deck and target at gesture start prevents mid-hold selection changes retargeting. Future Conductor/replay submits on the same seam under machine tenure; physical deck identities remain A–D even with two visible decks. This is a proposed minimal boundary, **not** a new framework. [Desktop deck snapshots](../../frontend/src/playback/DeckEngine.ts), [capture clock](../../frontend/src/capture/events.ts), [Conductor](../../frontend/src/sets/Conductor.ts).

## Device spikes, sizing and decisions

- On *two representative physical Android phones*, measure wired-speaker/headset tap→audible onset, cue-stab repeat/release, random seek and loop-boundary discontinuity; output stream callback burst, actual sample rate/performance mode, underruns/XRuns and route-change recovery. Test Bluetooth separately (device/codec buffering can dominate). Oboe explicitly says requested sharing/performance mode need not be granted and render callback must not block. [Oboe guide](https://github.com/google/oboe/blob/main/docs/FullGuide.md). **No measured latency figures yet.**
- Estimate only: uncompressed stereo float PCM at 44.1 kHz is `44,100 × 2 × 4 ≈ 353 KB/s`; one 5-minute track ≈106 MB decimal, four ≈423 MB, four 4-stem tracks ≈1.69 GB before copies/cache/DSP. Desktop browser's `bufferCache.ts` explicitly budgets ~1.25 GiB for 4-stem workloads; not a phone budget. Trial resident full decode vs bounded decoded seek-window cache; record warm/cold seek p50/p95, underruns, memory, battery/thermal at A/B then A–D. [desktop cache](../../frontend/src/playback/bufferCache.ts).
- Validate format matrix WAV/AAC/M4A/MP3 and actual user library formats, VBR time↔sample seek accuracy, 44.1→device-rate conversion, first playable frame, file URI access, backend HTTP Range, cache versioning and exact waveform/audio identity. The desktop's `FileResponse` Range and `MWF1` are available but the prototype has no device sync/login/offline protocol. [tracks](../../backend/routers/tracks.py), [waveforms](../../backend/routers/waveforms.py), [#152](../../docs/research/mobile-sync-protocol.md).
- Human decisions after spikes: pilot uses selected local file or desktop-authoritative offline transfer? Distribution terms for a GPL/commercial stretcher if Signalsmith does not pass? What measured phone/device/route and latency budget is acceptable? Whether scratch/4-deck/FX fidelity is pilot-critical versus next parity stage? Headphone cue/output routing may be deferred without blocking audible two-deck pilot. [#65](https://github.com/murtaza64/manadj/issues/65), [Rubber Band license](https://github.com/breakfastquay/rubberband/blob/master/README.md).

Proposed follow-up tickets: (1) device decode/seek/clock benchmark with self-created audio; (2) two-deck shared PCM mixer and command/snapshot contract; (3) MWF1/library identity + transfer decision; (4) gridded transport/key-lock/scratch performance probes; (5) FX/capture/Conductor/C-D parity and output-routing evaluation. These are proposed scopes, not claims that production readiness has been reached.
